Architecture - Sequence Design

MWAA Diagnostic Agent, Production Sequence

Extends the current CLI agent into something you can actually have a conversation with - ask how many DAGs failed in this environment, how many failed across every environment today, or why this particular DAG failed, then keep asking follow-ups in the same thread. All of it served behind an API, cached, and still schema-validated on the way out.

Participants

Twelve moving parts across two lifecycles: a background pipeline that keeps failure counts fresh, and an on-demand loop that answers a question.

UserAsks a question in plain English.
ClientSlack app, web console, or CLI - whatever surface took the question.
API + AuthAuthenticates the caller, rate-limits, routes to the orchestrator.
Agent OrchestratorRuns the tool-call loop and leans on Pydantic to validate every tool argument and the final answer against a schema - malformed output gets caught and retried before it ever reaches you.
ClaudeDecides which tool(s) to call and drafts the final structured answer.
Tool LayerThe @agent.tool functions, bound to a live MwaaClient.
CacheproposedShort-lived (~60s) read-through cache for repeat count queries. Not in mwaa_client.py yet.
Aggregation StoreproposedPre-computed failure counts by env / DAG / task / day. Layers on top of the live calls MwaaClient already makes.
SSM ProxyIn-VPC EC2 instance used only when the webserver is PRIVATE_ONLY. Shipped today.
Airflow REST APIThe environment's own API, reached via MWAA's InvokeRestApi. Shipped today.
CloudWatch LogsLast-resort log source when the REST log body comes back empty. Shipped today.
EventBridge / Ingest λproposedBackground listener that would keep the aggregation store current.

Background ingestion - continuous

recommended for efficiency

This is the path worth defaulting to for anything counting-shaped. It runs independently of any user question - every DAG/task state change lands in the store within seconds - so an aggregate question reads one pre-computed row instead of replaying the live Airflow API once per DAG. The cost per question stays flat as the environment grows; querying live wouldn't.

Request lifecycle - model, tools, follow-ups, failures

where every gate lives

Fig. 2 shows the two question shapes; this is the mechanics underneath both of them - what the model is actually deciding turn by turn, where a question can get rejected before it costs anything, and what happens when a step fails instead of succeeding.

How the model decides. Claude sees the system prompt, the conversation so far, and a JSON schema for every registered tool - the real tools plus a synthetic final_result tool generated from the output type. Each turn it either calls a tool (or several, in parallel) or emits final_result. There's no hardcoded call order in the code; the system prompt's suggested sequence (get_dag_runs → get_task_instances → get_task_log) is a strong hint the model tends to follow, not a switch statement.
How tool calling happens. Each @agent.tool function's parameters become part of Claude's request as a schema generated straight from the Python type hints - nothing hand-written to keep in sync. When Claude emits a tool call, the orchestrator matches it to the real function, injects the live dependency (MwaaClient today, the aggregation store once it exists), runs it, and feeds the result back as a new turn. Repeat until Claude stops asking for tools.
How follow-ups work. The CLI keeps message_history between questions in one session and passes it back in on the next call, so "what about yesterday?" doesn't need to re-establish which DAG or environment you meant. Memory isn't a shortcut around validation, though - every new question, follow-up or not, re-enters at the pre-validation gate below.
Failure scenarios. Three distinct kinds, and today only one of them is actually handled. A final answer that fails schema validation triggers an automatic retry, up to twice - that part is real, it's PydanticAI's built-in behavior. A request rejected at pre-validation never reaches the model at all - real once that layer exists. But a tool raising today (throttling, a denied private webserver, a timed-out proxy call) is not caught anywhere - PydanticAI only intercepts ValidationError and a tool-raised ModelRetry, neither of which the six tools in agent.py use. A raw boto3 exception today crashes the whole request. Wrapping each tool's AWS calls to catch expected failures and re-raise as ModelRetry(...) (proposed) is what would make "caught, sent as text" in fig. 3 true instead of aspirational.
Pre-validation - before the model runs. Belongs at the API + Auth layer, not inside the agent: is the caller authenticated, is the requested environment one they're scoped to see, is the question non-empty and under a length cap. Plain application code guarding cost and access - never something the model is trusted to enforce on itself.
Post-validation - after the model answers. This is Pydantic's job, and it's already in the code today: output_type=FailureDiagnosis is the schema Claude's final answer must satisfy, checked inside the orchestrator itself before anything is returned. A response that doesn't validate is never handed to the caller - it's fed back as a correction and re-attempted.

Design notes

The parts that make this "prod" rather than the current single-shot CLI.

The store replaces the fan-out. Answering "how many DAGs failed across the environment" by calling the live REST API once per DAG doesn't scale past a handful of DAGs and stalls chat latency. The ingestion pipeline pre-aggregates continuously so the counting path is a single indexed read.
Counting and root-cause are different tools, not different prompts. get_failure_summary (proposed, not in agent.py yet) would be purpose-built and bounded; the existing three-call drill-down (get_dag_runs → get_task_instances → get_task_log) stays untouched for narrative diagnosis.
The SSM proxy only guards the drill-down path. The counting path reads from the store, not live Airflow, so it's unaffected by a PRIVATE_ONLY webserver - only root-cause log fetches need the in-VPC fallback.
Cache absorbs repeat questions. A 60s TTL in front of the store means "how many failed" asked three times in one conversation costs one store read, not three.
Output stays schema-validated either way. Both branches would still exit through the same Pydantic-checked final_result tool - a count-style answer would just validate against a leaner FailureSummary model (proposed) alongside the existing, shipped FailureDiagnosis.

Not applied yet - efficiency & long-term accuracy

gaps, not nice-to-haves

Found by checking claims on this page against agent.py, mwaa_client.py, and PydanticAI's own source rather than against the earlier design intent. Ranked by actual payoff, not by how interesting each one is.

1. Tool failures should raise ModelRetry, not propagate raw. Checked directly in pydantic_ai/_tool_manager.py: it only intercepts ValidationError and a tool-raised ModelRetry - nothing else. None of the six tools in agent.py raise either, so a throttled or denied AWS call today is an unhandled exception that kills the whole request, not the graceful "evidence was inconclusive" fig. 3 implies. The fix is narrow: wrap each tool's AWS call, catch the expected exceptions, re-raise as ModelRetry("..."). Bounded by the same retries=2 already set on the agent - a correctness gap, not a hypothetical.
2. Prompt caching would cut cost on every multi-call chain. The root-cause path alone is three to four tool round trips (get_dag_runs → get_task_instances → get_task_log, plus retries), and each one resends the full system prompt and all six tool schemas - the same ~1-2K static tokens, rebilled every turn. Anthropic's cache_control on that block is a pure efficiency win with no behavior change, and the highest-value one here specifically because this agent is tool-call-heavy by design.
3. No observability trail exists past a single run's console output. PydanticAI ships instrumentation (instrument=True, OpenTelemetry) that isn't turned on anywhere in this codebase. Without it there's no record of which tool got called with what arguments, how long each step took, or where Claude changed its reasoning - across real usage, over months, as the model or prompt changes. That trail is what "long-term accuracy" actually depends on; right now nothing keeps it.
